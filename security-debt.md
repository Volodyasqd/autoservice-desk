# Аудит безпеки (OWASP Top 10) та план технічного боргу

**Проєкт:** AutoService Desk (веб-сервіс запису на автосервіс)  
**Дата:** Жовтень 2026  
**Автор аналізу:** Розробник команди (група КІ-21)

---

## 1. Чекліст безпеки за OWASP Top 10

| Категорія OWASP | Опис перевірки в проєкті | Статус |
|---|---|---|
| **A01: Broken Access Control** | Перевірка прав доступу до зміни статусів заявок лише для ролі адміністратора. | Потребує покращення |
| **A02: Cryptographic Failures** | Передача даних через захищений протокол HTTPS; відсутність чутливих даних у відкритому вигляді. | Пройдено |
| **A03: Injection** | Захист від SQL Injection у формі бронювання за допомогою prepared statements. | Пройдено |
| **A04: Insecure Design** | Наявність бізнес-обмежень (наприклад, ліміт записів на один часовий слот). | Потребує покращення |
| **A05: Security Misconfiguration** | Вимкнення відображення налагоджувальних стек-трейсів (debug mode) у продакшн-середовищі. | Пройдено |
| **A06: Vulnerable and Outdated Components** | Перевірка актуальності базових Docker-образів (Nginx/Redis) та сторонніх бібліотек на наявність CVE. | Пройдено |
| **A07: Identification and Authentication Failures** | Стійкість паролів адмін-панелі та блокування після серії невдалих спроб входу (brute-force). | Потребує покращення |
| **A08: Software and Data Integrity Failures** | Використання перевірених джерел базових образів та перевірка цілісності пакетів через хеш-суми. | Пройдено |
| **A09: Security Logging and Monitoring Failures** | Логування критичних подій: створення заявок, невдалі спроби авторизації в адмін-панель. | Потребує покращення |
| **A10: Server-Side Request Forgery (SSRF)** | Перевірка обробки зовнішніх URL-адрес сервером (вхідні запити не роблять сторонніх HTTP-викликів за вказівкою користувача). | Пройдено |

## 2. Список виявлених ризиків та вразливостей

1. **Відсутність Rate Limiting на публічній формі запису**  
   * **Severity:** High  
   * **Опис:** Користувач або бот може надіслати сотні фіктивних заявок за хвилину, заблокувавши доступ або переповнивши базу.  
   * **Запобігання:** Впровадити обмеження за IP-адресою (не більше 5 запитів на хвилину) та додати CAPTCHA.

2. **Можливість IDOR (Insecure Direct Object Reference) в API заявок**  
   * **Severity:** High  
   * **Опис:** За прямого звернення до endpoint `/api/booking?id=123` неавторизований клієнт потенційно може побачити дані іншого клієнта.  
   * **Запобігання:** Прив'язати перегляд деталей замовлення до унікального випадкового токена/UUID або вимагати авторизацію адміністратора.

3. **Слабкі вимоги до пароля адміністратора СТО**  
   * **Severity:** Medium  
   * **Опис:** За замовчуванням система дозволяє встановити простий пароль без перевірки на складність і довжину.  
   * **Запобігання:** Встановити мінімальну довжину від 10 символів із обов'язковим комбінуванням літер, цифр та спецсимволів.

4. **Відсутність централізованого логування підозрілих дій**  
   * **Severity:** Low  
   * **Опис:** Помилки вводу форми або спроби підбору пароля адміна фіксуються лише в загальному stdout-потоці контейнера, де можуть перезаписатися.  
   * **Запобігання:** Налаштувати запис подій безпеки у структурований JSON-лог.

5. **Відображення інформації про версію веб-сервера (Server Header)**  
   * **Severity:** Low  
   * **Опис:** Nginx за замовчуванням повертає заголовок `Server: nginx/1.25.x`, полегшуючи зловмиснику підбір експлойтів.  
   * **Запобігання:** Додати директиву `server_tokens off;` у конфігурацію `nginx.conf`.

## 3. Реєстр технічного боргу та план ліквідації на ітерацію

### Елементи технічного боргу:
1. **Код:** Необхідність винесення логіки валідації вхідних даних форми з контролера в окремий валідаційний сервіс.
2. **Тести:** Відсутність автоматизованих тестів на відмову при відправці некоректних спецсимволів (XSS / SQL-патерни).
3. **Інфраструктура:** Відсутність автоматичного оновлення базового образу Docker через сканер залежностей.

### План погашення на 1 спринт (Definition of Done — DoD):
* [x] Налаштувати ліміт запитів (Rate Limiting) засобами Nginx для роуту відправки заявки.
* [x] Приховати версію Nginx через директиву `server_tokens off;`.
* [x] Додати валідацію вхідних полів на заборону HTML-тегів (`<script>`, тощо).
* [ ] *(Свідомо відкладено на наступний реліз)* Повноцінна інтеграція SMS-шлюзу для сповіщень.

## 4. Рефлексія
Найбільш неочевидним ризиком виявився IDOR: на етапі створення прототипу здається, що передачі числового `id` достатньо, але без перевірки контексту користувача це створює прямий витік персональних даних клієнтів СТО.
